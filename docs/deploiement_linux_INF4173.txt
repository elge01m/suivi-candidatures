LOT 7 — SÉCURITÉ ET PRÉPARATION DU DÉPLOIEMENT LINUX

Ce document décrit des opérations futures. Aucune ressource cloud, installation
Linux, migration principale ou activation de service n'est exécutée par ce lot.
Les noms example.invalid sont des exemples publics non utilisables sur Internet.

Architecture et prérequis
Un serveur Linux maintenu (Ubuntu 24.04 LTS convient), Python 3.13, PostgreSQL 18,
Nginx, systemd et Node 24.22 pour construire React. Pas de Celery, Redis ni Docker
en production. Viser 2 Gio RAM, 1 vCPU, espace libre pour releases et sauvegardes ;
1 Gio peut être trop juste lors d'une sauvegarde ou d'un build. Construire React
avant la mise en service évite sa consommation mémoire pendant les requêtes.
Le serveur doit rester allumé ; le navigateur personnel n'héberge aucun worker.
Ne créer ni acheter de serveur, domaine ou autre ressource pendant ce lot.

Une origine HTTPS unique sert React et /api. Nginx -> Gunicorn 127.0.0.1:8001 ;
PostgreSQL 127.0.0.1:5432. Seuls 80/443 et SSH restreint à l'administrateur sont
exposés ; 5432, 8001 et les ports de développement restent fermés publiquement.
Pour une base distante : TLS verify-full + DB_SSLROOTCERT, jamais une vérification
désactivée. Les adresses et certificats réels restent à choisir et à vérifier.

Organisation des fichiers
/srv/suivi-candidatures/releases/<commit>/ : release immuable, propriété root,
  code lisible mais non modifiable par le compte système suivi.
/srv/suivi-candidatures/current : lien vers la release active.
/etc/suivi-candidatures/backend.env : root:suivi, mode 0640, dossier 0750.
/etc/suivi-candidatures/backup.key et backup.pgpass : opérateur seul, mode 0600.
/var/backups/suivi-candidatures : opérateur seul, mode 0700, hors racine web/code.
Le compte suivi n'a ni shell interactif, ni sudo, ni droit d'écriture sur le code.
www-data lit seulement le build React et les fichiers statiques nécessaires.
Ne copier aucun .env, .venv Windows, node_modules, archive, clé privée ou journal
depuis le dossier de travail dans une release. Utiliser un commit revu et un
export des fichiers suivis ; vérifier séparément les fichiers suivis sensibles.

Paramètres de production
Copier deploy/production.env.example vers le fichier externe et le compléter
dans un éditeur local privé. Le modèle ne contient aucun vrai secret.
DJANGO_SETTINGS_MODULE=config.production_settings et DJANGO_LOAD_DOTENV=0 sont
obligatoires. Ce mode ne charge jamais implicitement backend/.env.
DJANGO_SECRET_KEY doit être une clé aléatoire indépendante, au moins 50 caractères.
APP_ORIGIN est l'origine HTTPS sans chemin. DJANGO_ALLOWED_HOSTS contient des hôtes
exacts, séparés par des virgules, sans wildcard ni espace. Les origines CSRF sont
HTTPS et appartiennent à ces hôtes. GOOGLE_REDIRECT_URI doit être exactement
APP_ORIGIN + /api/gmail/callback/. OAUTH_SUCCESS_REDIRECT_URL est / ou la racine de
la même origine HTTPS. Aucun paramètre next fourni par le navigateur n'est suivi.
STATIC_ROOT est un chemin absolu externe aux sources publiques React.

Lors du transfert de données existantes, conserver EXACTEMENT les deux clés
Fernet existantes, distinctes : jetons OAuth d'une part, messages/analyses et
propositions d'autre part. Ne pas les régénérer : les données seraient illisibles.
Les sauvegarder séparément de la base dans un coffre chiffré hors ligne. La clé
de sauvegarde est une troisième clé indépendante. Ne jamais placer une clé dans
VITE_*, le navigateur, GitHub Actions, un argument de commande, une capture ou un
journal. Ne pas activer set -x ; ne pas afficher env, settings ou --print-config.
Les valeurs de tests publics sont fictives et ne doivent jamais être réutilisées.
La clé locale de développement anciennement écrite dans settings.py a été retirée.
Sans DJANGO_SECRET_KEY local stable, une reconnexion locale peut être nécessaire.
Les valeurs réelles de backend/.env n'ont pas été modifiées par ce lot.

Google Cloud, à effectuer seulement lors d'un déploiement autorisé
Enregistrer l'URI HTTPS exacte du callback pour le client OAuth Web ; conserver
les identifiants côté serveur. La session Lax est compatible avec le retour GET
OAuth ; CSRF reste imposé sur connect/login/logout et les écritures.
Ne pas désactiver CSRF, TLS ou les contrôles state pour contourner une erreur.
Le mode Testing Google peut limiter la durée des refresh tokens (notamment 7 jours
pour une application externe Testing avec gmail.readonly). Ce fonctionnement et
les éventuelles exigences de vérification Google restent à examiner avant un
usage durable. Aucun consentement ni appel Google n'est lancé dans ce lot.

   Contrôler nginx -t, chaîne TLS, renouvellement et droits de la clé privée.

Journaux et confidentialité
Nginx journalise seulement date, méthode classée, catégorie fixe de route, statut
et taille : ni IP, URI complète, code OAuth, query, cookie, referer, sujet ni corps.
Ses erreurs HTTP sont volontairement désactivées car elles peuvent copier une URL
de callback. Gunicorn n'a pas de journal d'accès. Les journaux Django/Gunicorn de
production éliminent arguments, exceptions, requêtes et piles ; diagnostics moins
détaillés, à compléter par les codes d'erreur persistants déjà disponibles dans
l'application. Ne jamais réactiver un logging brut pour diagnostiquer une boîte
réelle ; reproduire sur des données fictives dans un environnement isolé.
Installer si souhaité le modèle de rotation du journal sûr (7 jours), sans
archiver de données personnelles. Restreindre aussi l'accès au journal systemd et
sa rétention sur le serveur ; pas d'export automatique vers un service tiers.
PostgreSQL : vérifier log_statement=none, log_min_error_statement=panic,
log_parameter_max_length=0, log_parameter_max_length_on_error=0 et éviter les logs
de connexions. Restreindre les fichiers. Pour minimiser strictement les valeurs
dans les erreurs SQL, retenir log_min_messages=fatal et log_error_verbosity=terse
après revue opérateur (réduit les diagnostics). Ne jamais journaliser les requêtes
ou paramètres applicatifs. Rien de cela ne modifie PostgreSQL local dans ce lot.

Sauvegarde chiffrée et restauration de contrôle
deploy/postgres_archive.py utilise pg_dump -Fc, vérifie pg_restore --list, chiffre
l'archive Fernet en mémoire et relit le fichier chiffré avant succès. SHA-256 porte
uniquement sur le fichier chiffré. Limite 64 Mio d'archive non chiffrée : au-delà,
arrêt sans publier une sauvegarde tronquée ; prévoir une procédure streaming
revue séparément pour une base plus grosse. Pas de copie SQL en clair sur disque.
Éviter d'exécuter une sauvegarde pendant un pic mémoire ; ~plusieurs fois la taille
de l'archive peuvent être nécessaires en RAM. Toutes les données doivent provenir
d'une base de confiance : une restauration PostgreSQL peut exécuter du SQL.
L'outil ne sauvegarde pas les rôles système, ni les clés, ni backend.env.

Créer les dossiers privés et une nouvelle clé dédiée dans un terminal local privé
seulement lors de la mise en place autorisée ; exemple de génération sans affichage :
  umask 077
  set -o noclobber
  backend/.venv/bin/python -c 'from cryptography.fernet import Fernet; import sys; sys.stdout.buffer.write(Fernet.generate_key())' > /etc/suivi-candidatures/backup.key
Ne jamais écraser une clé existante ; choisir un nouveau fichier si elle existe.
Conserver cette clé séparément des archives, sauvegardée dans un coffre hors ligne.
Configurer PGPASSFILE en 0600 ; format hôte:port:*:rôle:mot_de_passe, valeurs privées
saisies dans l'éditeur, caractères : et \ échappés selon libpq. Ne pas utiliser
PGPASSWORD ou un mot de passe dans la commande ; l'outil refuse PGPASSWORD et le
retire du processus enfant. Une base distante exige PGSSLMODE=verify-full et
PGSSLROOTCERT. Un compte de sauvegarde doit avoir les droits de lecture utiles ;
la restauration de contrôle exige un opérateur autorisé à créer une base neuve.
Ne pas donner CREATEDB au rôle du service web pour cette seule opération.

Dans ce terminal, définir PGHOST/PGPORT/PGUSER/PGDATABASE/PGPASSFILE, BACKUP_DIR et
BACKUP_KEY_FILE (chemins seulement, sans afficher leurs contenus), puis :
  backend/.venv/bin/python deploy/postgres_archive.py backup --archive /var/backups/suivi-candidatures/NOUVEAU_NOM.fbackup
  backend/.venv/bin/python deploy/postgres_archive.py verify --archive /var/backups/suivi-candidatures/NOUVEAU_NOM.fbackup
  backend/.venv/bin/python deploy/postgres_archive.py restore-check --archive /var/backups/suivi-candidatures/NOUVEAU_NOM.fbackup --target restore_check_20261019_001
Le nom de cible doit utiliser uniquement minuscules/chiffres/underscore après
restore_check_. Toute cible existante est refusée ; ni DROP ni --clean n'existent.
Pour un clone destiné à être promu, ajouter --owner suivi_candidatures_app : le
rôle applicatif doit exister et l'opérateur doit pouvoir créer une base pour lui
et SET ROLE vers ce rôle. La base et les objets restaurés lui appartiendront ;
le rôle applicatif du service conserve NOCREATEDB. Sans --owner, le clone est
possédé par l'opérateur et ne doit pas être promu avant revue de ses permissions.
Le clone est conservé et ses configurations sont désactivées/bloquées restore_review.
Aucun worker, migration ou appel fournisseur n'est lancé. Contrôler les effectifs,
relations, déchiffrement avec les clés applicatives restaurées, sans les afficher.
verify prouve lisibilité/authenticité et lecture du catalogue ; seul restore-check
prouve la restauration complète. Conserver une copie CHIFFRÉE hors du serveur sur
un support existant autorisé ; aucune destination cloud n'est provisionnée ici.
Aucune politique de suppression automatique n'est ajoutée aux anciennes sauvegardes.

Promotion d'une restauration / retour arrière
Ne jamais restaurer par-dessus une base existante. Arrêter d'abord les écritures
de l'application et le timer/worker lors d'un incident réel autorisé ; prendre une
sauvegarde vérifiée et conserver la release et la base précédentes intactes.
Restaurer dans une NOUVELLE base de contrôle, vérifier ses données et clés, puis
faire approuver sa promotion. Pointer DB_NAME du fichier externe vers cette base
vérifiée, jamais par un remplacement SQL destructif. Avant d'enlever restore_review,
annuler les travaux hérités via reset_connection sur chaque GmailConnection sous
transaction et verrou (service existant), en vérifiant explicitement le nom de la
base cible. Cela conserve les jetons/messages, réinitialise consentements/baux et
annule les travaux ouverts. Réglages automatiques toujours faux ; aucune reprise
avant nouvelle validation opérateur et consentement humain. Cette étape reste
manuelle et n'est pas exécutée par le script de contrôle.
Pour une simple régression du code avec schéma compatible : arrêter suivi-web,
repointage atomique du lien current vers la release antérieure, contrôle de config,
puis redémarrage. Ne pas déplacer les venv ni recopier de secrets dans une release.
Si schéma incompatible, analyser d'abord la stratégie ; pas de migrate inverse
automatique, pas de suppression de colonne/table pour rendre le code compatible.
Après retour arrière : vérifier HTTPS, connexion, CRUD, propositions acceptées,
effectifs et traitements désactivés avant toute réactivation autorisée du timer.
